# ⚽ MatchMind — Agentic Match Intelligence Studio

**Inside the Game: Developer Hackathon (Microsoft × Premier League) submission.**

MatchMind turns a live stream of synthetic football events into explainable
match intelligence: real-time stats, tactical explanations, multi-language
narration and personalized viewing experiences — plus a player **Load & Risk
Monitor** grounded in sports science (ACWR).

> **Synthetic data only.** Every club, player, event and statistic in this
> project is fictional and generated by our own simulation engine. No real
> Premier League data is used. The eight clubs of the MatchMind Synthetic
> League echo the archetypes of English football (colours, regions, playing
> styles) but their names, kits and crests are invented; no real club name,
> nickname, badge motif or trademark appears anywhere.

## The five-stage pipeline

| Stage | Component | Status |
|---|---|---|
| 1. Ingest | Synthetic match engine + a positional model that places the 22 players every second + FastAPI/WebSocket live replay (configurable speed) | ✅ |
| 2. Interpret | Interpreter agent: team stats, xG race, momentum, per-player ACWR workload, team shape, heat maps and pressure on the ball | ✅ |
| 3. Explain | Analyst agent (gpt-4o, Agent Framework): *why* a moment matters, grounded in the Interpreter's numbers, plus a 10-minute forecast that the Judge grades | ✅ |
| 4. Render | Narrator agent (English analytical, casual, play-by-play, *relator rioplatense* 🇦🇷) + the broadcast UI (React): four seats, a pitch with the 22 players, shaded team blocks and heat maps, block-height and momentum strips, a pass network per team, a bench readiness board with risk curves and team load, lower thirds, what-if timelines, stadium sound and voice | ✅ |
| 5. Personalize | Director agent: decides per viewer (Analyst / Casual / Commentator / Player-Focus, language) which cards to show and how loudly; the Control room shows the same moment as two viewers got it | ✅ |

The Control room's pipeline map draws every component inside the stage it
serves, so the five stages are visible in the product, not only in this table.

## Architecture (target)

- **Azure AI Foundry** — model hosting (gpt-4o / gpt-4.1-mini) + evals
- **Microsoft Agent Framework** — multi-agent orchestration (Interpreter,
  Analyst, Narrator, Director, Load & Risk Monitor)
- **MCP server** — match-state tools exposed to agents
- **Azure Container Apps** (backend) + **Azure Static Web Apps** (frontend)
- Built with **GitHub Copilot** assistance

## Quickstart

```bash
cd backend
python -m venv .venv && .venv/Scripts/python -m pip install -r requirements.txt
.venv/Scripts/python -m matchmind.generate_match --home THU --away NBF --seed 42 --out ../data
.venv/Scripts/python -m pytest
.venv/Scripts/python -m uvicorn matchmind.api.app:app --port 8000
```

The simulator outputs an event stream (`*_events.jsonl`) and match metadata
(`*_meta.json`). The streamer replays any match in `data/` as a live feed:

- `GET /matches` — catalogue, `GET /matches/{id}/meta` — teams, squads, 28-day load history
- `WS /ws/matches/{id}?speed=10&mode=commentator&lang=es&player=THU-15` — every
  event in match-clock order (speed 1 = real time, 0 = instant); send
  `{"speed": 50}` or `{"profile": {...}}` to change speed / viewer profile live.
  Key events carry an Interpreter snapshot (score, team stats, xG race, momentum,
  per-player workload with live ACWR and risk alerts) and, a few seconds later,
  an `insight` message with the Analyst explanation, the Narrator line and the
  Director decision for that viewer.
- `POST /matches/{id}/branches` — **what-if**: re-simulate the match from a
  minute with a substitution or a tactical change. Same seed, so the branch is
  identical to the real match until that minute and diverges after; the
  response compares both timelines (score, xG, shots, injury concerns).
- `POST /mcp` — MCP server (streamable HTTP) exposing `list_matches`,
  `get_match_state`, `get_player_workload`, `get_risk_alerts`, `get_xg_race`,
  `get_risk_windows`, `get_analyst_credibility`, `get_team_shape`,
  `get_player_heatmap`, `simulate_intervention` to any MCP client. The same
  functions are the agents' tools.
- `GET /ws/matches/{id}?frames=auto|all|0` — positional frames ride the same
  socket as a side channel (`kind: "frame"`): every frame up to x60, one in two
  to x150, one in five to x400, none above; `all` and `0` override.

## AI that gets graded, not just heard

The **Load & Risk Monitor** predicts injury-risk windows per player from
observable workload only (live ACWR, minutes, sprint density, previous knocks,
metres-per-minute drop against the position norm). Because the simulator's
hidden fatigue produces observable `injury_concern` events, every prediction is
scored live: precision, recall, lead time, and where the player ranked among
everybody on the pitch when the knock happened. A naive baseline (risk = minutes
played) runs alongside with the same window policy (top 5 hazards on the
pitch), so the scorecard shows whether the model adds anything.

Offline evaluation over 40 simulated matches (`python -m matchmind.risk.evaluate --matches 40`):

| | Risk Monitor | Minutes-only baseline | Random pick |
|---|---|---|---|
| Knock happened to a top-3 hazard player | 32% | 16% | 14% |
| Knocks covered by an open window | 46% | 26% | |
| Mean warning time | 25 min | 18 min | |
| Windows that came true | 9% | 8% | |
| Alerts per match | 14 | 8 | |

Honest reading: the monitor ranks risk far better than chance or a minutes
heuristic, but most windows still pass without a knock. That is what the
scorecard is for. The hazard is a ranking score, not a probability: over 40
matches and 604 windows, those opened above 0.9 saw a knock 27 % of the time,
those below 0.8 almost never (`python -m matchmind.risk.evaluate
--calibration`). The bench seat draws that curve, with the current match's
windows on top, and hands the staff a post-match report (knocks and warning
times, Coach proposals with their branches, Analyst credibility) as JSON.

**Ground truth, stated openly.** The simulator's per-minute knock hazard is
convex in latent fatigue, spikes when the pre-match ACWR exceeds 1.3, and is
scaled by a latent individual susceptibility (0.5-1.0). The monitor never sees
fatigue or susceptibility; it only sees what leaks into the observables. The
knock model draws from its own random stream, so changing it never changes a
pass or a shot.

The **Coach agent** turns high-risk alerts into proposals, and the engine shows
the counterfactual branch of each proposal.

The **Analyst is graded too.** Every read ends with a forecast for the next 10
match minutes: which side creates more xG, the probability of a goal, and the
player most likely to be involved. The forecast goes into a ledger; when its
window closes, code settles each claim (dominance by xG created, the goal call
by a Brier score, the watched player by involvement in a shot, goal or knock)
and the **Judge agent** writes the verdict and the lesson in the viewer's
language. A naive forecast making the same three claims (the xG leader keeps
dominating, base-rate goal odds, the top shooter so far) is graded on the same
windows, so the Analyst's running credibility is
always shown next to a baseline, on the Analyst seat and in the Control room,
and is exposed to agents and MCP clients as `get_analyst_credibility`. Windows
close on the exact minute mark even when an insight arrives late at replay
speed, and nothing is forecast once the final whistle has gone.

Because the grading is code, the Analyst can be measured offline and improved
on evidence (`python -m matchmind.agents.evaluate_forecasts --matches 10`, same
seeds every run, the real Analyst on Foundry, ~66 forecasts):

| Analyst version | Overall | Who dominates | Goal odds | Player to watch |
|---|---|---|---|---|
| Naive baseline (xG leader keeps dominating, base rate, top shooter) | 0.64 | 0.68 | 0.94 | 0.32 |
| v1: season narrative only | 0.60 | 0.60 | 0.90 | 0.27 |
| v2: + last-10-minute window, game state, top shooters | 0.61 | 0.56 | 0.92 | 0.34 |
| v2 + the Judge's verdicts fed back (closed loop) | 0.64 | 0.58 | 0.92 | 0.39 |
| v3: + "dominance is xG, default to the xG leader" | **0.66** | 0.64 | 0.92 | **0.41** |

Honest reading: ten minutes of football are noisy, the naive rule is hard to
beat on "who dominates", and the Analyst only edges ahead overall after it was
given the recent window, its own graded record and a rule against reading
possession as dominance. The loop is real but small (+0.03 overall in the
ablation). The numbers are in `backend/eval/`.

## Agents

| Agent | Model | Job |
|---|---|---|
| Interpreter | none (pure Python) | Stats, xG race, momentum, ACWR workload per player |
| Analyst | gpt-4o | Explains why a key moment matters (structured output) |
| Narrator | gpt-4.1-mini | One commentary line per viewer profile and language |
| Director | gpt-4.1-mini | Picks the cards and priority each viewer gets |
| Load & Risk Monitor | none (pure Python) | Predicts risk windows from observables; self-evaluates against ground truth |
| Coach | gpt-4o | Proposes substitutions / tactical changes on risk alerts; the engine simulates the branch |
| Judge | gpt-4.1-mini | Reads each settled forecast (scores come from code) and writes the verdict and the lesson |

All agents run on **Azure AI Foundry** through the **Microsoft Agent Framework**
(Python). A deterministic key-moment gate decides when they wake up, so cost and
latency stay predictable (~3-6 s per moment). Try them from the CLI:

```bash
.venv/Scripts/python -m matchmind.agents.demo --limit 3 --mode analyst --mode commentator:es --mode player_focus:en:THU-15
```

**The words are checked too.** Whether the Analyst's reads and the Narrator's
lines are substantiated by the numbers they were given is scored with the
**Azure AI Evaluation SDK** (`GroundednessEvaluator`, gpt-4.1-mini on Foundry
as the judge, scale 1-5) over every cached agent output of a match
(`python -m matchmind.agents.evaluate_groundedness --match THU-NBF-40`). On the
headline fixture, 28 items: Analyst mean 4.86 (12 scored 5, 2 scored 4),
rioplatense Narrator mean 5.0. The two 4s flagged tactical inferences that go
a step beyond the numbers, which is the right place for an analyst to be
challenged. Results in `backend/eval/`.

## The commentator speaks

On the fan seat every narration line is voiced with **Azure AI Speech**
HD voices in an excited style: a Mexican Spanish voice reading the rioplatense
script (there is no rioplatense HD voice yet) or an American English one. The Foundry resource is a multi-service Azure AI
Services account, so the same key speaks; `GET /tts?text&lang` synthesises a
line once and keeps the MP3 under `data/cache/tts`, so a replay served from
the agent cache costs no Speech calls either. The desk's sound switch mutes
the crowd and the voice together.

## Fidelity, honestly

Every match is synthetic, and the players you see moving are too. The engine
emits events with coordinates (passes, shots, tackles, interceptions, fouls)
and no positions in between. A **positional model** (`sim/tracking.py`) then
places the 22 players once per match second: anchored on a 1-4-4-2, the block
shifts and compresses with the ball, defenders press the carrier, and every
placed event becomes an appointment (the passer is at the pass, the receiver at
its end, the shooter at the shot) so the picture never contradicts the data. It
is deterministic per seed, runs on its own random stream and never touches the
engine, so event ids, agent caches and the Risk Monitor evaluation are
unchanged. From those frames the Interpreter measures **team shape** (block
height, width, compactness, line heights, phase), per-player **heat maps**
(12x8 grid in team frame), **pressure on the ball carrier** and a per-minute
**block height series**. The Analyst reads them in its context and cites them
in metres ("block at 37.7 m, compact at 21.1 m"), MCP clients ask for them, the
fan seat draws the players and the heat, and the analyst seat adds the shaded
blocks on the pitch, a block-height difference strip, the Analyst's read in
metres kept on screen, goal markers on the xG race, pressing rates and a pass
network per team (links come from passer and receiver in the events; nodes
sit where the positional model has each player on average).

What this is not: tracking data. A real feed comes from cameras or GPS units
and the positions drive the events, not the other way round. The honest next
step would be an emergent simulation, 22 agents with velocity, acceleration
and decision rules from which passes and shots arise, validated against the
distributions of real matches (speeds, distances, pass lengths). That is a new
engine and would invalidate today's evaluation numbers and caches, so it is
future work, and the UI labels positions as a positional model wherever they
appear.

## Built for several viewers at once

A replay is deterministic, so every agent output is cached per (match, moment,
viewer profile) and written through to `data/cache/`: the first viewer pays the
Foundry call, everyone after gets the same explanation instantly, and the
Control room says "from cache". Degraded results are never cached. Each live
stream also has its own view of the match in the state registry, so the agent
tools read the caller's minute even when another viewer is at full time;
MCP and REST clients outside any stream see the latest view. Before a demo:

```bash
.venv/Scripts/python -m matchmind.agents.warm_cache   # all matches, the four seat profiles
```

## Who would use this

- **Performance and medical staff**: the Risk Monitor turns the workload they
  already track (GPS distance, sprints, 28-day load, ACWR) into warnings with
  a lead time, and keeps an honest scorecard of how often it was right. Nothing
  in the method depends on the data being synthetic.
- **The coaching bench**: a readiness board of the XI (hazard, ACWR live vs
  pre-match, recent effort against the player's own pace, open risk windows),
  the substitutes still available and the five-changes-in-three-windows budget;
  the Coach agent proposes a substitution or a tactical change on a high-risk
  window, the engine shows the counterfactual, and the bench can try its own
  change from the same card; every decision taken or tried lands in a decision
  log and in the full-time report. Each risk score comes with its empirical
  frequency from the calibration (how often windows like this one saw a
  knock). Warning time is the bench's credibility number: mean minutes of
  notice before a knock, next to a minutes-only rule, shown as a count until
  three knocks exist.
- **Broadcasters and fans**: the same match personalised by seat and language,
  with every agent decision traceable in the Control room.

## Orchestration

Key moments run as a Microsoft Agent Framework workflow: `ConcurrentBuilder`
fans the moment out to the Analyst and the Narrator, the Director takes their
structured outputs. Middleware records every agent run and tool call into a
trace that the Control room seat renders as swimlanes. If the workflow fails,
the moment is served through direct calls and the trace says so.

## Responsible AI note

The Load & Risk Monitor is **decision support, not medical advice**. It flags
workload patterns (acute:chronic workload ratio, sprint density, fatigue
proxies) on synthetic athletes for illustrative purposes only.
